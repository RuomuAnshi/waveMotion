## 这是什么

WaveMotion 是一个**完全在本机运行**的音乐可视化背景生成工具。选一段音频，它离线分析节拍与能量，你用六种视觉模板逐个试、调参数、实时预览，最后导出 1080p / 1440p 的 MP4。

定位是**剪辑用的背景素材**，所以：

- 画面里**不会**叠加标题、封面或 Logo
- 默认使用**完整音频长度**
- 导出可选择**保留原音**或**只出画面**（静音素材给后期配音用）

## 快速开始

### 前置要求

| 依赖 | 版本 | 说明 |
|---|---|---|
| Node.js | ≥ 22 | 跑前端与本地服务 |
| Python | 3.12 | 离线音频分析（librosa） |
| FFmpeg | ≥ 6 | 探测音频信息、封装 MP4 |
| Chrome / Chromium | 任意近期版本 | Remotion 渲染后端 |

### 安装

```bash
git clone https://github.com/RuomuAnshi/waveMotion.git
cd waveMotion

# 1. 前端与服务依赖
npm install

# 2. 创建隔离的 Python 环境（不会污染全局 Python）
npm run setup:python

# 3. 把素材放进 assets/（仓库不包含素材文件）
#    assets/wav.wav
#    assets/背景.mp4     # 仅作为风格参考，不参与渲染

# 4. 启动（同时拉起 Fastify 本地服务与 Vite 前端）
npm run dev
```

打开终端里输出的地址（默认 `http://127.0.0.1:5179`）即可使用。

生产模式则先构建再启动，由 Fastify 同时托管前端与接口：

```bash
npm run build
npm start          # → http://127.0.0.1:3210
```

## 视觉模板

六种模板共用同一套节拍与能量驱动系统，但画面语言各不相同：

| 模板 | 画面表现 | 音频响应 |
|---|---|---|
| **渐变几何脉冲** | 黑底实心渐变圆盘放大，休止段收回圆盘 | 拍点触发向外扩散、变细并消失的描边，连续插值颜色和尺寸 |
| **霓虹光环** | 多层同心光环、辉光、旋转轨迹 | 拍点扩散，频段能量改变环形轮廓尖刺 |
| **镜像频谱** | 中心对称的频谱条阵 | 频谱驱动条高，拍点增强亮度与整体缩放 |
| **粒子星场** | 有纵深的粒子漂移与放射 | 低频推动速度，瞬态触发粒子爆发 |
| **几何隧道** | 连续多边形环向中心收缩 | 拍点驱动推进，能量控制旋转与纵深 |
| **流动光场** | 大面积色块、柔光、流动波纹 | 能量驱动形变，拍点产生中心扩散波纹 |

模板内部按**拍点计数**与**能量变化**调整构图、颜色和强度，并在段落切换时插入短转场以保持风格连贯。首版不自动混合多个模板。

## 音频分析与画面驱动

分析使用 **Python 3.12 + librosa + FFmpeg** 离线完成，由 Node 后台以子进程调用。一次分析产出：

- 音频时长、自动 BPM、拍点时间、起音事件
- 整体响度包络、低／中／高频能量、32 个频谱频段
- 节奏稳定性提示（用于提醒用户是否需要手动校正）

分析始终使用**降采样单声道副本**；播放和导出**保留原音频的声道与内容**。结果按「音频内容 + 分析版本」缓存，切换模板、改颜色、调强度都不会触发重新分析。

当前分析版本为 `analysis-v2`：频谱按逐帧顺序输出，低／中／高频使用非负幅度归一化。旧版本缓存会自动失效并重新分析，无需删除原素材或项目。M4A、AAC、WebM 等 libsndfile 无法读取的格式会通过 FFprobe 读取原始元数据，再由 FFmpeg 解码分析副本；支持 `WAVEMOTION_FFMPEG` 和 `WAVEMOTION_FFPROBE` 指定可执行文件。

### 同步规则

- **自动模式**直接使用检测到的拍点，而不是按平均 BPM 匀速播放——真实的音乐不是节拍器
- **手动修改 BPM** 后，改用「BPM + 起拍偏移」生成规则拍点；能量与频谱仍来自真实分析数据
- **半速／双速**改变视觉响应节奏；**偏移只移动视觉拍点，不移动音频**
- 拍点决定**动作时机**，频谱与能量决定**幅度**；采用快速响应、平滑回落，避免画面抖动
- 静音段自动降低运动强度；节奏不明确时提示校正，并保留能量驱动效果
- 每 4／8 拍的变化通过拍点计数实现（首版不承诺自动识别小节或强拍）

### 确定性

所有动画都由**当前帧 + 分析数据 + 固定随机种子**计算得出，没有任何跨帧状态。粒子和隧道同样支持直接跳转到任意帧——这既是 Remotion 的渲染要求，也保证了**预览与成片完全一致**、重复渲染结果可复现。

确定性分两层验收，因为「逻辑完全相同」和「像素完全相同」不是一回事：

| 层次 | 验证方式 | 判定 | 命令 |
|---|---|---|---|
| 动画逻辑 | 遍历 513 帧逐字段比对、打乱帧序访问、纯函数重入 | **0 差异（严格）** | `npm run verify:acceptance:engine` |
| 像素输出 | 同帧重复渲染、跳帧 vs 顺序渲染 | 视觉等价：max ≤ 8/255 且 PSNR ≥ 45 dB | `npm run verify:acceptance:determinism` |

像素层用容差而不是「逐像素 0 差异」，是因为 Chromium 的 GPU 分块光栅化在同一台机器上存在间歇性竞态：同一帧两次渲染，多数情况逐像素完全相同，偶发约 1.3M 像素相差 4/255（呈水平条带，PSNR ≈ 54 dB）。这属于光栅化噪声，不影响画面内容。实测过 `egl`／`angle-egl`／`swangle`／`swiftshader`／`vulkan`、以及 `--disable-gpu-rasterization`／`--disable-partial-raster`／`--num-raster-threads=1` 等组合：能把单帧差异压到 0 的，整片就会丢条带（最多 189/513 帧损坏）；能保证整片完整的，就仍会偶发抖动。**在本机 Metal 上这两个性质互斥**，而整片完整性是用户能直接看到的，优先级更高，所以默认保留 `angle`，并把「动画逻辑 0 差异」放到不经过 GPU 的引擎层严格把关。

## 输出规格

| 比例 | 1080 级 | 1440 级 |
|---|---|---|
| 横屏 16:9 | 1920×1080 | 2560×1440 |
| 竖屏 9:16 | 1080×1920 | 1440×2560 |
| 方形 1:1 | 1080×1080 | 1440×1440 |

- 全部支持 30 / 60 fps，默认 **1920×1080 · 30 fps**
- MP4 使用 H.264 + `yuv420p`；保留音频时使用 AAC
- 时长按音频样本数计算并向上对齐到整帧，末尾误差小于一帧
- 每次输出使用唯一文件名，绝不覆盖已有成片

导出参数在**提交时生成快照**，之后继续编辑界面不会影响正在渲染的任务。后台一次执行一个导出任务，其余自动排队；支持取消、失败重试和错误原因展示。

## 验收脚本

`tests/` 下是完整的验收脚本，覆盖 README 末尾「验收标准」里的每一条。它们会自己合成测试音频、自己启动渲染，不依赖 `data/` 里的历史产物。

```bash
npm run verify:acceptance:bpm          # 5 组已知 BPM 的合成击拍，比对检测精度
npm run verify:acceptance:edge         # 半速/双速/手动偏移 + 静音/弱音/无节拍/损坏音频
npm run verify:acceptance:frames       # 预览帧 vs 成片帧逐像素对比（PSNR）
npm run verify:acceptance:engine      # 动画逻辑确定性：513 帧逐字段 + 打乱帧序（0 容差）
npm run verify:acceptance:determinism  # 像素确定性：同帧重复渲染 + 跳帧渲染（视觉等价容差）
npm run verify:acceptance:integrity    # 整片画面完整性：逐帧扫描丢条带
npm run verify:reference-style         # 参考风格行为 + 横竖屏黑底与缺条带区分
npm run verify:audio-regressions       # 频谱时间定位、频段响应、容器解码、拍点配对、缓存版本与配色
npm run verify:acceptance:outputs      # 5 组输出规格 + 队列/取消/重试（需先启动服务）
npm run verify:acceptance:project      # 项目配置保存/载入/导入导出（需先启动服务）
npm run verify:acceptance:ui           # 真实浏览器验证模板参数记忆（需先启动服务）
```

需要 `assets/wav.wav` 的脚本会在缺失时给出提示。Chrome 路径可以通过 `WAVEMOTION_CHROME` 覆盖，Python 通过 `WAVEMOTION_PYTHON` 覆盖。

## 验收标准

- 用已知 BPM 与起拍偏移的合成节拍音频检查分析：稳定节奏的 BPM 误差 ≤ 1%，校正后的视觉触发误差 ≤ 1 帧
- 覆盖半拍／双拍、开头静音、低音量、无稳定节拍、损坏音频等边界情况
- 用 `assets/wav.wav` 实际试听检查踩点，完成六种模板的导出样片
- 对比预览与导出的同一帧；重复渲染粒子画面验证确定性
- 用 FFprobe 核对分辨率、帧率、时长、编码与音轨；验证取消、失败后可以重新导出
- 人工检查动感、构图变化、背景留白与竖屏裁切，确保不是"只换配色"

## 实现说明

- **音频分析**：librosa 的节拍追踪受 STFT hop 量化限制，解析度约 11.6 ms。分析阶段对拍点序号与时间做最小二乘线性回归重新估计速度，把 BPM 误差从 0.94% 降到 0.033%。
- **节拍显著性**：单纯用拍点规律性判断会因为纯噪声也得到规整的伪拍点。分析会比较拍点位置与反拍位置的起音强度，得到「节拍重音是否明显」的独立指标，再与稳定性加权成置信度；不明显时主动提示用户手动校正。
- **导出音轨**：视频用 Remotion 渲染为纯画面（H.264 / `yuv420p` / BT.709），再用 FFmpeg 以 `-c:v copy` 把原音频封装进去。这样既不二次编码视频，也不会因 Remotion 的音频路径产生时长漂移；成片时长严格等于帧数 / 帧率。
- **像素格式**：Remotion 默认可能输出 `yuvj420p`（full range）。导出时显式指定 `colorSpace: "bt709"`，保证得到 `yuv420p` + TV range，兼容常见播放器与剪辑软件。
- **确定性**：所有动画由「当前帧 + 分析数据 + 固定种子」纯函数计算，没有跨帧状态；粒子和隧道不依赖上一帧位置，因此可以随机跳帧渲染。`src/engine` 与 `src/remotion` 内不出现 `Math.random`／`Date.now`／`performance.now`，随机性统一走 `mulberry32` 种子哈希。
- **渲染后端**：导出默认使用 `gl: "angle"`，因为它是唯一能稳定产出「整片画面完整」成片的后端。用 1920×1080×513 帧整片、每后端连渲两次实测：`angle` 两次均 0/513 帧损坏；`egl` 77/513、`angle-egl` 51~72/513、`swiftshader` 52~66/513 帧损坏——单帧尺寸与 ffprobe 元数据全部正常，但画面只画出顶部若干水平条带、其余纯黑（Remotion issue #11428 的 GPU 光栅化失败），只有逐帧像素扫描才能发现。`swangle` 虽然完整，但速度慢约 10 倍且跨次差异极大（PSNR 20 dB），不可用。
  注意不要用「同帧 renderStill 重复渲染」来选后端：`egl` 在这项上确实是 12/12 轮逐像素 0 差异，但那只测单帧，测不出整片丢条带。**单帧确定性 ≠ 视频帧完整性。**
  可用环境变量 `WAVEMOTION_GL` 覆盖；整片完整性由 `npm run verify:acceptance:integrity` 把关，导出流程本身也会逐帧扫描，损坏帧超过 5% 直接判失败并提示原因（`WAVEMOTION_SKIP_INTEGRITY=1` 可跳过）。扫描以大面积纯黑筛出候选，再检查上下镜像位置不匹配的近全黑水平行；黑底圆盘、对称留黑和纯黑尾帧不会仅因黑色面积大而被判为损坏。这是检测单侧缺条带的启发式检查，不是所有画面异常的通用判定。
